# Known limitations

Everything I know does not hold, or have not tested, and the rules install and the uninstaller apply when they decide what is this tool's. The README keeps the short list.

## Limits and untested paths

- **No test runs against a real system.** Every Homebrew, `softwareupdate` and `pmset` answer the tests use is a hand-written fixture, not output captured from a live Mac. Make your first run a supervised one: `check`, then `auto --dry-run`, then a `run` you watch. Two things only a real run can show: whether macOS's App Management protection lets Homebrew replace an app during a pass the schedule started, and whether a folder downloaded as a ZIP carries a quarantine attribute that stops the window from opening (the installed copy's `verify` reports one).
- **macOS versions.** The tool needs `jq`, `plutil` with its `raw` output format (added in macOS 12), and a `lockf` that locks an open file descriptor (`lockf -s -t 0 9`, the form current macOS documents). With an older `lockf`, every mode that changes things, the installer and the uninstaller would stop at the lock rather than run without it; I reasoned that from the code and have not tried it on an old release. I have run the test suite only on a recent macOS release on Apple silicon; I have not tested older releases. Homebrew under `/usr/local` (Intel Macs) is detected by the code, but only the static tripwire checks that branch; no test runs it.
- **Interactive upgrades.** In the interactive pass, Homebrew's own quit is left on (the tool has already asked before quitting the app itself), so Homebrew may also quit other apps that the cask's uninstall steps name. For an `assisted` app, Homebrew runs the cask's uninstall steps for the old version (see What Homebrew itself can remove, below). If you close the window while an app is being replaced, the replacement finishes in the background without the run lock, so give it a minute before you start another pass.
- **An app opened during an unattended upgrade.** The pass checks that an app is closed right before it hands it to Homebrew, but Homebrew downloads first and then replaces the bundle, and with its own quit off it does not check again. An app you open in those seconds can be replaced while it runs.
- **A file where a Homebrew link goes.** If a file that is not a link sits where a cask puts a command-line link, a shell completion or a man page, or where one of that path's folders should be, Homebrew's upgrade fails on it, Homebrew's attempt to restore the old version fails on the same file, and undoing that attempt can remove the app (I read this in Homebrew's source and have not reproduced it on a live Mac). So this tool never adopts or upgrades such an app, in any mode. `check`, `setup` and every pass that reaches the Dock inventory (`run`, `auto`, and `scheduled` after your yes) name the file. A pass in which Homebrew lists that app as outdated, once you have confirmed it and unless it is in the `vendor` or `manual` group (then this tool never upgrades it and only warns), also records a failure (`in-the-way(APP)` in `history.tsv`), so the unattended pass asks for you. Setup skips the adoption and says why. While the app matches the index, the file is only a warning and the pass completes, because nothing would be upgraded; the failure appears in the first pass that finds an upgrade waiting. It checks the paths Homebrew links for `binary`, `command_wrapper`, the four shell completions (bash, zsh, fish and PowerShell) and `manpage`, once in the inventory and again right before Homebrew is called. A folder among those paths that this account cannot write would make Homebrew ask for the administrator password, which a slot cannot answer, so such an app is `assisted` and only an interactive pass upgrades it.
- **What that check does not see.** It reads the paths from the current cask definition, but Homebrew's restore links the installed version's paths, so a file at a path only the older version used is not seen; it matters only when the upgrade fails for another reason, because the restore then fails on it. A link at a path only the new version uses that points somewhere else also fails the upgrade. Completion files a cask generates are not links and are not checked (such casks are never `silent`). And a file created in the seconds between the last check and Homebrew's link is not seen. In those cases the same double failure can still remove the app; if the app is gone afterwards, the pass says the app is missing, not only that the upgrade failed.
- **Homebrew's `brew.env` files.** Homebrew reads `HOMEBREW_*` lines from `/etc/homebrew/brew.env`, `<prefix>/etc/homebrew/brew.env` and `~/.homebrew/brew.env` (or `homebrew/brew.env` under `$XDG_CONFIG_HOME` or `$HOMEBREW_XDG_CONFIG_HOME`, when one is set) after the environment, and those lines win. So a `HOMEBREW_CASK_OPTS=--no-binaries` line there reaches every upgrade and drops the cask's command links, although this tool clears that variable, and a line there can override the other Homebrew settings this tool exports. The tool does not read those files; check them if links go missing.
- **A Homebrew that cannot refresh its index.** Every slot defers with exit status 0, and the notification says the index could not be refreshed. Once no pass has finished for `heartbeat_days`, a slot also sends a notification that says so.
- **Untested branches.** No test exercises the `slow_warn` warning (the setting is at least 60 seconds, and no scenario runs an upgrade that long), `install.sh` refusing a Mac without Homebrew or `jq`, or `check` naming a missing tool: the sandbox cannot hide `/usr/bin/jq`, and the test seam requires the Homebrew double. For the same reason no scenario runs without `caffeinate` (the seam requires its double), and none makes `pgrep` fail while keep-awake is released; in that case keep-awake is not signalled and ends with the run instead, at the latest when the closing prompt times out.
- **Keep-awake release timing.** Keep-awake is signalled only after `pgrep` confirms the saved process number still belongs to the runtime's own `caffeinate` child. A window of milliseconds remains between that check and the signal, in which the child could end and macOS could hand its number to another process.
- **Whose a loaded schedule is.** To tell, the uninstaller and install read the `program =` line of `launchctl print` for the labels they have to judge (`docs/ARCHITECTURE.md`, "Is the installed schedule current?", lists them), which Apple documents as not an interface. If a macOS release drops that line, both stop with exit status 1 and name the schedule instead of guessing; `launchctl bootout gui/$(id -u)/LABEL` removes it by hand.
- **Unusual home folder paths.** A home folder path with `&`, `<`, `>`, `"` or `'` is not supported: the LaunchAgent cannot be rendered, so install exits 2, and without the install manifest the uninstaller exits 1. A LaunchAgent this tool wrote while `HOME` was spelled with a different letter case is not matched to its runtime either, except the one the install manifest names: the uninstaller then stops with exit status 1 instead of guessing, and so does install when that agent is at its own label or loaded under another one (otherwise install names it and leaves it alone).
- **Temporary files.** bash 3.2 writes each here-document to a temporary file in `/var/tmp`, then `/tmp`, then `/usr/tmp`, and ignores `TMPDIR`. If none of those can be written, those inputs read as empty, bash prints "cannot create temp file for here document", and a report can be wrong. A normal Mac always has a writable `/var/tmp`.
- **Install that stops part-way.** `./install.sh` unloads the old schedule before it moves the old files aside. If a later step fails, or you interrupt it, the old schedule stays unloaded; rerun `./install.sh` to load the schedule your config names.
- **Background items.** On recent macOS versions, System Settings, General, Login Items lists LaunchAgents like this one under Allow in the Background. If it is switched off there, no slot runs, and nothing tells you, because the heartbeat notification comes from a slot. I have not checked that on a live Mac; `status` lists the latest history rows.
- **Test time.** `tests/run-all.sh` takes about 15 to 20 minutes under the sandbox I use for the tests, which slows process start-up, and longer on a busy Mac.

## What Homebrew itself can remove

The tool itself deletes nothing, but each upgrade is an ordinary Homebrew cask upgrade, and two things in it are Homebrew's, not this tool's. Homebrew replaces the links the cask defines (commands, shell completions, man pages), as it does when you upgrade by hand; an adoption leaves the command links out, and the app's next upgrade adds them, once the check above has found every one of those paths free or already a link. A cask that generates its shell completions has Homebrew delete and rewrite the file at each of those paths, even one you placed there by hand; such a cask is never upgraded unattended. And when you let the interactive pass upgrade an app that needs a person (group `assisted`), Homebrew runs that app's own uninstall steps for the old version, which can remove files or helpers the app installed.

## How install and the uninstaller decide what is this tool's

A *weekly-update label* is made of ASCII letters, digits, dots and hyphens, does not start with a dot, and ends in `.weekly-update`; only such labels are unloaded, and only such labels are asked about.

- With the install manifest in place, the uninstaller unloads the schedule loaded under the label the manifest names and moves the LaunchAgent there, whatever they run, because install wrote them.
- If the tool folder was already removed by hand, it also asks launchd about the schedule your config names, and unloads it if it runs this tool.
- Either way, it looks at every other `*.weekly-update.plist` too. One whose Label is its file name and a weekly-update label, and whose program is this tool's runtime, such as the agent of an older label after `label_prefix` changed, is unloaded and moved the same way. The runtime path counts as this tool's when its home part is your home folder, spelled with a trailing slash, with doubled slashes or through a symlink.
- An agent with the same suffix that runs another program, or names no program it can read, is named and left in place. When this tool's LaunchAgent sits at a label whose loaded schedule runs another program, the file is moved and that schedule stays loaded.
- When it cannot tell whose something is, it stops with exit status 1 before anything is unloaded or moved: a `*.weekly-update.plist` it cannot read (including a link to a missing file), this tool's runtime path under another home folder (such as a renamed one), an agent that runs this tool but whose Label is not its file name or not a weekly-update label, or a loaded schedule whose program launchctl does not name. So does an install manifest (hand-edited) whose label is not a weekly-update label; install instead warns and leaves that label alone. So does a LaunchAgent that cannot be rendered (an unreadable config, for example) when there is no manifest and no LaunchAgent of this tool is found; when it did find one, it removes that one and then exits 1, because the label the config names went unchecked. Its `--dry-run` exits 1 in these ownership cases; in the render case where it found an agent, the dry run exits 0 with the same warning. A pass in progress, or a tool folder where it cannot make `removed-DATE/`, is found only by the real run, which then unloads and moves nothing and exits 1; its dry run exits 0.
- Install applies the same rule at its own label before it unloads or moves anything: it stops with exit status 1 when the LaunchAgent there cannot be read, or when it or the schedule loaded under it runs another program or names no program it can read, unless this tool's own install manifest names that label. A reinstall then unloads and moves aside what is at the label the manifest names, whatever it runs, and so does install for an older label the manifest names after `label_prefix` changed. Install also unloads and moves aside another label's LaunchAgent that runs this tool, when the schedule loaded under that label, if any, runs this tool too; it stops with exit status 1 when that schedule names no program it can read or this tool's runtime path under another home folder. A LaunchAgent under another file name that runs this tool's runtime path under another home folder stops install the same way while a schedule other than another program's is loaded under the label its Label key names, when that is a weekly-update label (a lookalike whose Label key is not one is named and left alone without asking launchd); otherwise it is named and left alone, as are a file it cannot read, one that names no program it can read, one whose Label is not its file name or not a weekly-update label, and this tool's file at a label where another program is loaded. Under any other label whose LaunchAgent runs another program, it does not look at the loaded schedule, even when that schedule runs this tool, unless such a lookalike file carries that label as its Label key; `launchctl list | grep weekly-update` shows such a label. `./install.sh --dry-run` exits 1 for these ownership stops; a pass in progress or a tool folder it cannot write to is found only by the real install, which then unloads, moves and installs nothing and exits 1 (a first install may leave behind the empty folders and the empty `run.lock` file it made).

## What the uninstaller does and keeps

It unloads the schedule, moves the installed copy and its LaunchAgent into `~/.local/share/weekly-update/removed-DATE/` (with `-2`, `-3` added when that folder exists), and checks that they are gone ("Removed and verified", exit 0). If it cannot make that folder, it unloads and moves nothing and exits 1. Anything else it cannot unload or move is listed, with exit status 1.

Kept: the log folder `~/Library/Logs/weekly-update` (its records and the `run.lock` file), your config in `~/.config/weekly-update`, and the dated `replaced-*` and `removed-*` folders under `~/.local/share/weekly-update` (and a `staging-*` folder, if an install stopped part-way). To remove the files it left, delete those three folders yourself. Nothing is deleted by the uninstaller.

It cannot find a schedule that launchd still has loaded under a label whose `*.weekly-update.plist` is gone, runs another program or names no program it can read, and that the install manifest does not name (without the manifest, that your current config does not render either), for example when that file was moved by hand while the schedule was loaded; `launchctl list | grep weekly-update` shows such a label. If you linked the runtime into a folder on your `PATH`, remove that link yourself.

The same steps by hand, if you prefer: `launchctl bootout gui/$(id -u)/LABEL` (the label is the file name, without `.plist`, of the `~/Library/LaunchAgents/*.weekly-update.plist` whose program is `~/.local/share/weekly-update/app/bin/weekly-update`), then move that plist and `~/.local/share/weekly-update` wherever you like.
